# GitHub PR Explorer — Release Notes v1.0.0

**September 4, 2026** · covers September 2 – 4

This is the first tagged release. Versions are tracked as git tags from here on.

v1.0.0 finishes the automated review pipeline from v0.9.0 and makes it
something you can run unattended. The short version: authors can push back on
findings and get a follow-up without a human touching the tool, reviews can no
longer take down the machine, and the pipeline tells you what it is doing on
the PR itself.

---

## Highlights

### 🤖 Pipeline overlay — one place to see every PR in automation

Click the **🤖 button in the header**. You get a sortable, filterable table of
every PR the pipeline knows about, with a **Stage** column that says where the
PR is and *why* (waiting on CI, behind base, reviewing, verdict posted,
mediation, and so on).

- Search, filter by stage, repo, reviewer, badge, or number of review rounds.
- Expand any row for the review log, verdict composer, audit, timeline, notes,
  and criteria overrides — the same tools you had on board cards.
- Select several rows and bulk **opt out / re-enroll / arm / disarm / watch on
  board**.
- Opens instantly from a cached snapshot and refreshes in the background; a
  freshness indicator shows how old the data is.

The old protected **Auto swimlane is gone.** Automation no longer writes to the
board or the merge queue. The board is your hand-picked watch list again, and a
PR can be armed for auto verdicts whether or not it is on the board. The
pipeline table has moved out of the Automation tab, which is now config only.

### 🙋 Re-request a review and the pipeline follows up

When an author clicks **Re-request review** on GitHub, the tool picks it up and
runs a follow-up review. No extra API calls, no manual step.

- The follow-up prompt reads the PR conversation since the last review: issue
  comments, inline threads, and review replies. If the author answered a
  finding with a rationale instead of a code change, the reviewer sees it.
- Findings the author addressed in comments are recorded as **withdrawn** or
  **disputed**, and a **Dispositions** section appears in the posted verdict.
- Follow-ups only re-review the diff and the previous findings. Unchanged text
  is not re-litigated.
- PRs that were opted out or had failed are re-enrolled by a review request.
  Cards show a **Review requested** badge; pipeline rows show
  **Follow-up requested**.

### ⚖️ Disputed and deferred findings, and mediation

Review loops on design docs used to never converge: a disputed finding sat in
its severity section and counted against the threshold every round.

- Reviews now have **Disputed** and **Deferred** sections. Findings there keep
  their severity but **do not count** toward the critical/major/minor limits.
- If enough critical or major findings are disputed (default **3**, adjustable
  per PR), the PR goes to **mediation**: auto verdicts are disarmed, the review
  is posted as a comment rather than a verdict, and a status comment routes the
  PR to a human. The pipeline shows a sticky **mediation** stage and a locked
  badge so it is easy to find.
- Reviewers no longer state a verdict in their write-up. The configured criteria
  decide; any leftover "Verdict-leaning" lines are stripped before posting.
- The old **Recommendations** section is gone. It only ever restated the
  per-issue Fix lines.

### 🛡️ Reviews can't take down the box anymore

After the August 31 hang, review runs are fenced off:

- Every review gets its own throwaway shallow git workspace under
  `~/.cache/gh-pr-explorer/review-workspaces`. Reviews never touch developer
  checkouts.
- Reviews are killed after **60 minutes** (configurable) and handed to the
  normal retry policy.
- Each review subprocess runs in a systemd scope capped at **12 GB memory and
  256 tasks**, so a runaway run cannot OOM the machine or fork-storm.

### 💬 The PR tells you what the pipeline is doing

Every pipeline event posts a short status comment on the PR: enrolled, waiting
(and on what), review started, retry scheduled, gave up, verdict deferred,
mediation. At most **one** status comment stands per PR at a time; old ones are
replaced, and posted verdicts are never touched. Bulk backfills stay silent so
enrolling a hundred PRs does not blast a hundred comments.

All of this is behind the existing `post_review_started_comment` flag.

## Also in this release

- **GitHub rate limit handling.** A verdict that hits the API quota is
  deferred and retried with backoff (5 min → 1 h, gives up after 24 h) instead
  of being lost. The follow-up watcher now makes one call per repo per cycle
  instead of one per armed PR.
- **Persistent logs.** Process logs go to `logs/pr-explorer_<UTC start>.log`
  per run plus an append-only `logs/error.log`. Old run logs are pruned after
  30 days (configurable); `error.log` is never pruned.
- **Re-enrolling works.** A PR re-enrolled after its dispatch window expired
  now waits the full window again instead of being skipped immediately.
- **`requireBaseBranch`** gate (default `main`) and an optional
  **`dispatchTimeoutHours`** cutoff for waiting PRs.

## New configuration

| Setting | Where | Default | What it does |
|---|---|---|---|
| `mediationDisputedThreshold` | Auto Verdict criteria / per PR | 3 | Disputed critical+major findings that trigger mediation |
| `requireBaseBranch` | Automation tab | `main` | Only dispatch PRs targeting this branch |
| `dispatchTimeoutHours` | Automation tab | 0 (wait forever) | Optional cutoff for waiting PRs; 0 = wait forever |
| `review_timeout_minutes` | `config.json` | 60 | Wall-clock kill for a single review |
| `review_workspace` | `config.json` | root `~/.cache/gh-pr-explorer/review-workspaces` | Block: root, fetch depth, fetch timeout, sweep age for throwaway review checkouts |
| `log_retention_days` | `config.json` | 30 | Prune per-run log files; 0 disables |
