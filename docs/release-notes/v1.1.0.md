# GitHub PR Explorer — Release Notes v1.1.0

**September 11, 2026** · covers September 4 – 11

Analytics is rebuilt from the ground up around a local daily rollup instead of
live GitHub Stats API calls. It's faster, covers a repo's full history instead
of a 52-week window, and no longer burns GraphQL/REST quota on every tab
switch.

---

## Highlights

### 📊 Analytics, rebuilt on a local daily rollup

The Analytics tab is now three sub-tabs — **Stats**, **Activity**,
**Contributors** — all reading from one endpoint backed by a precomputed
per-developer, per-day table (`analytics_daily`) that the background sync
worker keeps current. The **Lifecycle** and **Reviews** sub-tabs, and their
five GitHub-Stats-API-backed endpoints, are gone.

- **Windowed, with custom dates.** A shared window picker (All time / 1D / 1W /
  1M / 3M / 6M / 1Y, or a custom begin/end range) and a base-branch selector
  drive all three sub-tabs together. "All time" now means the repo's actual
  earliest PR, not a 52-week cap.
- **Stats** gets a **Table ⇄ Time series** toggle: the table has a pinned
  **Team** totals row, and the time series view lets you pick multiple metrics
  and multiple people at once (up to 16 series), per-day or cumulative.
- **Activity** shows team-wide daily charts (commits, lines added/deleted,
  PR counts) instead of weekly ones.
- **Contributors** overlays one line per person for a single metric
  (commits, lines added, lines deleted, merges, reviews), with Show all/Hide
  all controls.
- **Bot exclusion.** Bot accounts (`app/`-prefixed and `[bot]`-suffixed
  logins, plus a configurable `analytics.bot_logins` list) never show up in
  the numbers.
- **Avg review rounds**, team and per-developer: the average number of
  completed code-review pipeline runs a merged PR went through before
  merging, shown alongside Avg merge time in the Stats table and as a
  time-series metric. Only merged PRs that actually went through the review
  pipeline count toward the average.
- The view renders instantly from whatever data is already synced, and
  quietly re-polls every 15 seconds while a repo's history is still backfilling
  — no spinner-gated wait.

### 🕰️ History backfill to repo inception, and commit sync

The PR sync worker no longer stops at a 180-day window:

- An **inception history walk** paces itself backward from today to a repo's
  creation date, a budgeted slice per cycle, so old closed/merged PRs
  eventually get fully synced without a one-time GraphQL spike.
- **Commit sync** is new: commits on configured branches (default `main`) are
  synced via the REST commits API, independently of PR sync, and feed the
  Analytics rollup's commit/line-count metrics.
- **`retain_days`** replaces the old unconditional prune: old CLOSED/MERGED
  rows are kept forever by default (`retain_days: 0`), so history isn't
  silently discarded once the rollup depends on it.

## Also in this release

- **Known limitation:** per-commit line stats are not tracked; Analytics lines
  come from merged PRs, attributed on their merge day.
- **Known limitation:** if incremental commit sync ever falls behind by more
  than `commit_pages_per_cycle × 100` commits, it logs a warning and keeps the
  high-water mark moving rather than stalling; a backlog that large needs a
  manual resync to fully close.
- A one-time migration (`drop_legacy_analytics_caches`) drops the old
  `developer_stats`, `stats_metadata`, `pr_lifecycle_cache`,
  `code_activity_cache`, and `contributor_timeseries_cache` tables. It runs
  automatically on first startup after upgrading.

## New configuration

| Setting | Where | Default | What it does |
|---|---|---|---|
| `pr_sync.retain_days` | `config.json` | 0 | Prune CLOSED/MERGED rows older than this; 0 = never |
| `pr_sync.history_backfill_budget` | `config.json` | 60 | `gh pr view` hydrations per cycle for the inception walk |
| `pr_sync.history_chunk_days` | `config.json` | 30 | Created-date window width per history search |
| `pr_sync.min_graphql_remaining` | `config.json` | 1500 | Best-effort: history walk skips a slice when `gh api rate_limit` reports GraphQL remaining below this; `history_backfill_budget` is the hard bound on hydrations |
| `pr_sync.commit_branches` | `config.json` | `["main"]` | Branches whose commits are synced |
| `pr_sync.commit_pages_per_cycle` | `config.json` | 40 | REST commit pages (100 each) per cycle, per branch |
| `analytics.bot_logins` | [CONFIGURATION.md](../../CONFIGURATION.md) | `["github-actions", "coderabbitai", "greptile-apps", "cursor", "claude", "copilot-pull-request-reviewer", "dependabot", "scalazack"]` | Logins excluded from Analytics attribution |

**Removed:** `review_sample_limit` — it only ever bounded the old
Lifecycle/Reviews sampling, which no longer exists.

---

## Rollout

Restart the server; the history and commit backfill runs in the background
over roughly **30 minutes** per repo before Analytics has full-history
coverage (the tab is usable immediately from whatever is already synced —
`syncing: true` and a "Syncing…" indicator show while it catches up). No
manual migration step: the legacy analytics tables are dropped automatically
on that first startup.
