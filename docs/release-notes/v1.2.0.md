# GitHub PR Explorer — Release Notes v1.2.0

**September 16, 2026** · covers September 12 – 16

Review findings are now classified in two tiers — **Blocking** and
**Non-Blocking** — instead of Critical / Major / Minor. The auto-verdict criteria
follow suit, every stored review is migrated on first start, and the reviewer
agents emit the two-tier report.

---

## Highlights

### 🚫 Blocking / Non-Blocking replaces Critical / Major / Minor

The three-way split added calibration noise without changing outcomes: the
verdict only ever cares whether a finding must be fixed before merge.

- **Two report sections.** Every review carries `Blocking Issues` (must be fixed
  in this PR) and `Non-Blocking Issues` (everything else worth reporting), plus
  the existing Disputed / Deferred set-asides on follow-ups. Review JSON is now
  **schema 2.0.0** with section types `blocking` / `non_blocking`; the
  `severity` recorded on disputed/deferred issues uses the same two values.
- **Mapping.** Critical and Major fold into Blocking (critical issues listed
  first); Minor becomes Non-Blocking. The reviewer agents keep their per-rule
  Critical / Major / Minor / Advisory calibration internally and use it only to
  decide which of the two sections a finding lands in.
- **Everything else is unchanged:** disputed/deferred handling, mediation, comment
  mode, follow-up scope, the no-verdict rule for agents, scores and highlights.

### 🧭 Reviewers report problems, never solutions

Findings no longer carry a `Fix`. Each issue states what is wrong, where, and
what it causes; the author decides how to address it.

- The review prompt forbids proposing a fix, replacement text, corrected code
  or a recommendation, and the reviewer agents drop their `Fix` field and
  fix-authoring rules in favour of a *No Proposed Fixes* section.
- The save path strips any `fix` an agent still emits, so no solution reaches
  the database, the UI, a verdict body or an inline comment.
- Reviews stored before this release keep their historical Fix lines. The
  verdict composer keeps its per-issue Fix editor so a human can add a remedy
  when posting.

### 🤖 Auto-verdict criteria: `maxBlocking` and `maxNonBlocking`

- `maxBlocking` (default **0**) replaces `maxCritical` + `maxMajor`; `maxNonBlocking`
  (default **unlimited**, stored as `null`) replaces `maxMinor`. Leave the
  Non-blocking field blank in the criteria form for no limit.
- The mediation threshold now counts **disputed blocking** findings.
- Existing global config and per-PR overrides are upgraded as
  `maxBlocking = maxCritical + maxMajor`, `maxNonBlocking = unlimited`, so a PR that
  tolerated one Major keeps tolerating one blocking finding.
- Status comments, verdict reasons, card badges, the pipeline Issues column and
  the Review Logs hover read `N blocking, M non-blocking`.

### 🗄️ One-shot data migration (`severity_two_tier_v1`)

Runs automatically on the first start of this version, once, and is recorded in
the `migrations` table:

- Rewrites every `reviews.content_json` to 2.0.0 (sections merged, disposition
  severities remapped); unparseable rows are left byte-identical.
- Backfills `auto_verdicts.blocking_count` / `non_blocking_count` from the legacy
  count columns (unknown stays `NULL`), sums the inline-posting counters, and
  upgrades every stored criteria snapshot, the global config and per-PR overrides.
- `scripts/migrate_severity_two_tier.py --db <path> [--dry-run]` runs the same code
  for a rehearsal on a copy or an explicit pre-restart run with a printed report.
- Legacy documents are also folded **on read** everywhere content is loaded, so a
  row restored from an old backup can never be tallied as zero issues.

> **Upgrade order matters.** Migrate only under this version: the previous
> build does not know the two-tier section types. Flip the reviewer agent files to
> the two-tier headings only after the app is running this version — until then
> the save path folds their Critical / Major / Minor output automatically.

### 💬 Inline comments per tier

The card's three post buttons are now two — 🔴 Blocking and 🟢 Non-Blocking — with
their own posted flags (`inline_comments_posted` stays the blocking flag;
`non_blocking_posted` is new). Disputed / Deferred are never posted inline.

## API changes

- `GET/PUT /api/auto-verdict/config` and `PUT /api/prs/…/auto-verdict/criteria`:
  `maxBlocking` (int ≥ 0) and `maxNonBlocking` (int ≥ 0 or `null`). Payloads in the
  old shape are folded before validation.
- Card / pipeline payloads: `blocking` / `non_blocking` `{posted, found, titles}`,
  `blockingPostedCount` …, `nonBlockingPosted`, `blockingCount` / `nonBlockingCount`
  on the last auto verdict.
- `GET /api/review-logs`: `issue_counts` is `{blocking, non_blocking}`.
- `GET /api/reviews/<id>/section-issues?section=` and
  `POST /api/reviews/<id>/post-inline-comments`: `section` is `blocking` (default) or
  `non_blocking`.
- `review_section_names` config keys: `blocking`, `non_blocking`, `disputed`, `deferred`.
